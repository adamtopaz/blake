# lazy-init: Blake's start-up is a third of `noop`; most of it is initializing Lean modules the build path never uses

- **Date:** 2026-10-31
- **Author:** Claude (Opus 5.5) with Adam Topaz, machine `2e698309` (i9-14900K, 16 of 32 CPUs, 32 GB cap)
- **Outcome:** inconclusive (investigated and measured; the change it calls for is larger than one iteration)
- **Branch / PR:** research/lazy-init-log (no code branch: the experiments were throwaway relinks, described below) — https://github.com/adamtopaz/blake/pull/14
- **Result files:** none (nothing was measured with the harness)

## Hypothesis

After `header-stub`, `noop` is the scenario furthest from "free": about 85 ms in the
harness (57 ms bare), of which, by earlier estimates, ~35 ms is Lean's module
initialization and ~45 ms is building the job graph. Every Blake invocation pays the
first part, `leaf` included (0.34 s). The hypothesis was that much of the start-up
initializes Lean machinery that `lake build` on a TOML workspace never uses (the
elaborator, the builtin parsers, the compiler), and that it can be skipped or
deferred.

## What was done

Measurements only, on CPUs 16-31, medians of 20-30 runs.

**1. Start-up of the current binary.** Blake (`.lake/build/bin/lake`, statically
linked, 242 MB):

- `blake --version`: 31.6 ms; stock `lake --version`: 36.1 ms; `true`: 1.4 ms.
- `blake build` on an up-to-date copy of `medium-deep`: 84.5 ms.
- The dynamic loader takes ~0.25 ms (`LD_DEBUG=statistics`: 758k cycles, 181k
  relative relocations), and `strace` shows ~20 ms of pure computation with no
  system calls. So start-up is Lean module initialization, not loading.

**2. Where it comes from.** I built tiny executables against the toolchain (in a
scratch package): `def main : IO Unit := pure ()` plus one import each. Each main
was patched to call `lean_initialize_runtime_module()` instead of
`lean_initialize()`, so only the imported modules get initialized:

```
no imports (Init only)        2.1 ms
Lean.Parser.Basic             2.3 ms
Lean.Environment              3.1 ms
Lean.Data.Json                3.5 ms
Lean.Message                  7.9 ms
Lean.Parser.Module           14.6 ms   (the builtin parsers)
Lake.Util.Log                27.9 ms   (61 MB RSS)
Lake.Config.Workspace        27.7 ms
Lake.Toml                    28.1 ms
Lake.CLI.Main                28.2 ms
```

Lake modules cost the same whatever they import because the Lean compiler emits a
call to `lean_initialize()` in the runtime initializer of every module of a
package that imports `Lean` modules (see `runtime_initialize_Lake_Util_Log` in
`.lake/build/ir/Lake/Util/Log.c`). `lean_initialize()` initializes all of Lean,
and it also makes the linker pull all of Lean into any executable that uses a Lake
module (4 MB becomes 114 MB).

**3. Wrapping `lean_initialize`.** I linked with `-Wl,--wrap=lean_initialize` and
a stub that calls only `lean_initialize_runtime_module()`, which leaves every
module to its own runtime initializer:

- `Lake.Util.Log`: 4.4 ms.
- An executable importing what a TOML `lake build` needs (`Lake.Build.Run`,
  `Lake.Load.Toml`, `Lake.Build.Module`): 15.6 ms (17 MB RSS).
- Blake itself relinked this way still builds the TOML corpus (`noop` and an edit
  both work). But its `noop` takes 83.4 ms against 84.9 ms, because `LakeMain`
  imports `Lake.CLI.Main`, whose closure includes 1230 `Lean` modules (1002 of them
  elaborator, meta, parser, compiler or server). Their runtime initializers cost
  about as much as `lean_initialize()` itself.

So wrapping `lean_initialize` alone gains ~1.5 ms. The gain requires that a TOML
build never initializes the heavy modules at all. Closure sizes (modules, and how
many are `Lean.*`):

```
Lake.CLI.Main            2522 modules, 1230 Lean.*, 1002 heavy
Lake.Load.Toml            953 modules,  176 Lean.*,   72 heavy
Lake.Build.Run            885 modules,  170 Lean.*,   66 heavy
Lake.Util.Log             513 modules,   56 Lean.*,    3 heavy
```

Most of the remaining 15.6 ms of the light set is `Lean.Parser.Module` (14.6 ms on
its own). It comes in through `Lean.Elab.ParseImportsFast`, which `Lake.Build.Module`
uses to read headers and which `public import`s `Lean.Parser.Module`. The TOML
parser (`Lake.Toml`) also builds on `Lean.Parser`.

Other things checked and ruled out along the way:
- Starting a dependent before its import finishes writing: `strace` of a `lean`
  compile shows the `.olean` written only ~9 ms before exit; the `.ilean` and
  `.c` follow within a millisecond.
- Critical-path priority for compile jobs: `medium-deep` is ~12 chains wide, so on
  16 CPUs compile slots rarely queue.
- Lean's import reads `.olean`s sequentially (`importModulesCore`), with no knob to
  parallelize it.

## Measurements

No harness runs; the numbers are above. Potential, from those numbers: if a TOML
`lake build` initialized only its light set, Blake's start-up would fall from ~30
ms to ~15 ms. Without `Lean.Parser.Module` it could reach ~5 ms. That is ~15-25 ms
off every invocation: harness `noop` from ~85 ms to ~60-70 ms (`noop` speedup vs
stock Lake from 2.0x to ~2.4-2.8x), and `leaf` ~5-7% faster.

## Conclusion

The idea is sound and is probably the largest gain left for `noop`, but it is a
restructuring, not a tweak. A plan for the next attempt:

1. **Lazy initialization:** link `lake` with `-Wl,--wrap=lean_initialize` and a C
   stub that only does `lean_initialize_runtime_module()`. Export a
   `blake_full_initialize` that calls `__real_lean_initialize()` and the full CLI's
   initializer once.
2. **A light root:** `LakeMain` imports only the modules needed to build a TOML
   workspace (CLI parsing for `build`, `Lake.Load.Toml`, the workspace and
   manifest loaders, `Lake.Build.*`). Anything else first calls
   `blake_full_initialize`, then the full CLI through an `@[extern]`/`@[export]`
   pair. The full CLI's objects must still be linked, for example through the
   `Lake` static library in `moreLinkObjs`, since the root no longer imports them.
   Fallback cases: a `lakefile.lean` anywhere in the workspace, any command other
   than `build`, unusual options.
3. **Keep heavy modules out of the light set.** In particular, read headers without
   `Lean.Parser.Module`. `ParseImportsFast` itself is small; check whether
   `Lake.Toml` really needs the builtin parser tables.
4. The test suite exercises `lakefile.lean` paths heavily, so it will catch a
   missing full initialization. A module used before its initializer ran fails
   fast: its closed terms are null.

`lakefile.lean` workspaces (still most of the ecosystem) would gain only the ~1.5 ms
of step 1. This is a general optimization for TOML workspaces (the default of
`lake new`), not benchmark-specific, but the write-up should say so.
