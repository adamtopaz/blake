# fork-lean: compile modules in forked children of a pre-initialized `lean` driver

- **Date:** 2026-10-30
- **Author:** Claude (Opus 5.5) with Adam Topaz, machine `2e698309` (i9-14900K, 16 of 32 CPUs, 32 GB cap)
- **Outcome:** success
- **Branch / PR:** research/fork-lean — (pending)
- **Result files:** research/results/20261031T003346Z-2e698309-9a95eef.json (commit `9a95eef`), research/results/20261031T011544Z-2e698309-ad55938.json (commit `ad55938`, the PR's code)

## Hypothesis

Earlier entries established that after Blake's own overheads were cut, the time of
`hub`, `cold`, and chain-bound `swarm` builds is inside `lean`. Each `lean` run
pays a fixed start-up cost: `exec`, dynamic linking of `libleanshared`, and Lean's
initialization (`--profile` reports `initialization` 20-33 ms), before it reads
its source.

The `lean` executable is a thin C++ wrapper (`lean_main`, `src/util/shell.cpp` at
v4.35.0) around Lean code: `lean::initializer`, then `lean_init_search_path`,
`lean_enable_initializer_execution`, option parsing through
`lean_shell_options_process`, `lean_io_mark_end_initialization`, a task manager,
and `lean_shell_main` (`Lean/Shell.lean`), which elaborates and writes the
`.olean`, `.ilean`, and `.c`. All of these are exported by `libleanshared.so`. A
process that has run `lean_initialize()` once can `fork()` and run the rest in the
child, i.e. exactly `lean`'s code path minus the start-up.

Measured before writing any Blake code, with a 100-line C test program linked
against the toolchain's `libleanshared`: for five `medium-wide` modules, the forked
children wrote `.olean`/`.ilean`/`.c` byte-identical to `lean`'s, and each took
23-31 ms less (385 vs 413 ms, 457 vs 480, 571 vs 600, 359 vs 390, 517 vs 548).

Blake itself cannot be the parent: it has initialized Lake's modules too, whose
environment extensions would then be registered in the child and could end up in
the `.olean`s it writes. So the parent is a separate helper, `blake-zygote`,
linked against the toolchain's `libleanshared` and initialized exactly like
`lean`.

Change: build `blake-zygote` (`c/blake_zygote.c`, a `target` in `lakefile.lean`,
a `need` of the `lake` executable) next to Blake's binary. `compileLeanModule`
sends each compile to an idle zygote from a pool (started on demand, one per
concurrent compile) instead of spawning `lean`. The child runs the steps above
with `LEAN_PATH` set and its stdout/stderr in temporary files, and the zygote
returns the exit code. The zygote is used only when the toolchain's `Init.olean`
records Blake's own `Lean.githash`; on any failure Lake runs `lean` as before.
Zygotes are stopped at the end of every build.

Expected: no change for a build that compiles one module (a fresh zygote pays the
initialization itself), ~25-30 ms saved for every further module a zygote
compiles: a few percent of `cold` and `hub` CPU, and more on chain-bound `swarm`
(`deep`/`layered`), where those ~25 ms sit on the critical path of every step.

## What was done

- `c/blake_zygote.c` (new, ~150 lines): the zygote. `main` calls
  `lean_initialize()` and `lean_set_panic_messages(true)`, then loops: read a
  request, flush, `fork`. The child opens `/dev/null` and the two output files
  onto fds 0-2, `setenv("LEAN_PATH", ...)`, and runs `child_main`, a transcription
  of `lean_main` after `lean::initializer` with the same `getopt_long` table and
  option string. It runs `lean_shell_main` on a 64 MB-stack pthread. The parent
  `waitpid`s and prints the exit code.
- `lakefile.lean`: `target blakeZygote` compiles it with `buildLeanO` and links it
  with the toolchain's `cc` against `-lleanshared` (rpath to the toolchain's
  `lib/lean`) plus `ccLinkFlags (shared := true)`. The `lake` executable `needs`
  it, so `lake build` builds it.
- `Lake/Build/Actions.lean`: `zygoteFor?`, `runLeanZygote` (pool of idle zygotes,
  request/reply, outputs via temp files), `prestartZygote`, `stopZygotes`; in
  `compileLeanModule`, the zygote path with `rawProc` as fallback and the same
  verbose command log. `Lake/Build/Run.lean`: `stopZygotes` after the monitor in
  `runFetchM` and `runBuild`. `Lake/Build/Library.lean`: a background task starts
  one zygote early if some module's source is newer than its trace.
  `Lake/Config/InstallPath.lean`: `initOleanHasLeanGithash` is public.
- Second commit `ad55938`: `stopZygotes` first asks every zygote to stop and only
  then reaps them. The first version reaped each before asking the next, which
  serialized up to 16 process exits at the end of a build.

Correctness: the zygote's outputs were byte-identical to `lean`'s in the C test
and in a direct protocol test. `nix develop -c tests/run_all.sh --compare
.out-main` gave 93 passed, 0 failed for both commits. The quick harness and the
held-out corpora reported `identical artifacts to lake, all builds ok, break
check ok`, which includes no processes left behind. A no-op build starts no
zygote (`strace -f -e execve`).

Before the standard sweeps, a non-standard A/B on `medium-deep` (cold, leaf,
swarm, hub; `main` vs candidate) gave cold 1.051x (584.5 s vs 562.3 s of CPU),
leaf 1.008x, swarm 1.036x (improved), hub 1.026x. That was without the early
start; with it, a hand-timed leaf on `medium-wide` was 1.065x.

## Conclusion

A real but modest gain, consistent with the ~25-30 ms of start-up that each
compile no longer pays, and only where a zygote serves several compiles. Across
both sweeps:

- `leaf` 1.03-1.05x on every corpus (under the 7% threshold);
- `hub` 1.01-1.05x (`wide` improved in the second sweep);
- `swarm` on `deep` 1.03-1.04x (improved in the first sweep);
- `cold` 1.00-1.03x.

Two results go the other way, within thresholds and in both sweeps, so probably
real:

- `swarm` on `wide` (0.968x twice): 24 modules compiled at once start ~16
  zygotes that each compile only one or two modules, so they pay the
  initialization anyway, plus a `fork` and a shutdown.
- `noop` (0.94-0.98x in the second sweep, mixed in the first): no zygote is started,
  but the early-start check scans every module's source and trace mtimes on a
  dedicated thread during the build.

The whole thing rests on running `lean`'s own driver code (`lean_shell_main`) in a
process initialized exactly like `lean`. The outputs are byte-identical by
construction, and the harness confirms it.

Next:

- Make the early start cheaper or smarter, e.g. reuse the mtimes already read
  during discovery instead of a second pass, or start a zygote only when the first
  module turns out to be stale.
- Keep zygotes for longer than one build (not allowed by the harness's
  no-helper-outlives-the-command rule unless measured as a separate feature).
- Size the pool to the expected number of compiles, so that small rebuilds like
  `swarm` on `wide` reuse a few zygotes instead of starting 16.
- Save the remaining per-child costs: `fork` of a process with Lean initialized,
  and the copy-on-write faults when the child marks the initialization's objects
  persistent (`lean_io_mark_end_initialization`). Marking them in the zygote
  before forking would avoid the faults, but `lean_main` runs
  `lean_init_search_path` and option processing while still initializing, so that
  order would have to be kept by other means.
- Windows: `c/blake_zygote.c` uses `fork`; see the caveat in the idea entry.
